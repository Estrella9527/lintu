# 匹配策略与部署架构

> 写于 2026-04-28。背景：UGC 站点 `https://ugc.example.com` 上同时承载多个景区（漂流 / 山地公园 / 后续更多）的 UGC 活动。AI 生成的文案中存在跨项目"互荐"现象——漂流文里推一句山地，反之亦然。需要规划：
> 1. 匹配策略如何处理"以 A 项目为主、可能涉及 B 项目"的查询
> 2. 本地 sidecar 如何对外提供服务给公网 UGC

---

## 第一部分：匹配策略

### 1. 现状诊断

**问题观察**：试匹配输入"漂流"相关文本，结果几乎全是山地公园的图。

**根因（不是模型变差）**：

| 链路位置 | 行为 |
|---|---|
| 前端 MatchPlaygroundTab | 不传 `project_id` |
| 后端 `match_text_to_images` | `filters.project_id = None` |
| `text_search.index_cache.get_or_build(None)` | 构建一个**所有项目合并**的 IndexShard |
| 排序池 | 山地公园 ~2000 张生成图 + 漂流 ~数百张 → 混在一个池里 |
| 结果 | 高频形态（山地）掩盖低频形态（漂流），即使 query 明确说"漂流"也被淹没 |

**关键认识**：embedding 不完美，相似度有噪声。同一个 query 的真匹配和噪声匹配的得分可能差 0.05 以内。当某项目体量是另一项目的 5-10x 时，**纯按体量比例就会出现"高频项目永远赢"的偏置**。

这就是为什么"原来准确"——之前库里只有山地，没有竞争。加了漂流后问题暴露。

### 2. 设计目标（被业务用例反推）

业务实际诉求：

| 用例 | 期望行为 |
|---|---|
| 漂流活动文案，纯讲漂流 | 8 张全是漂流图 |
| 漂流活动文案，文末提一句山地 | 6-7 张漂流，1-2 张山地（"互荐"图） |
| 山地活动文案，纯讲山地 | 8 张全是山地 |
| 跨项目推广文案（运营后台用） | 多项目自然分布 |

**不能用纯硬过滤**（filters.project_id=A 直接排除 B），那样"互荐"用例就死了。

**必须有"主项目"概念**，加一点跨项目 leakage 但受控制。

### 3. 推荐策略：主项目优先 + 跨项目融合（multi-shard recall + business boost）

#### 算法

输入：`text`, `primary_project_id`（来自 ApiKey 绑定）, `cross_project_ratio`（默认 0.2）

```
1. 召回（recall）：
   for each project_id in [primary, *others]:
     shard = index_cache.get_or_build(project_id)   # 已经按项目分片
     emb_hits[project_id] = top-K(shard, query_vec)  # K = limit * 4
   kw_hits[any] = recall_by_keywords(text, project_id=None)  # 关键词召回不限项目

2. 候选池融合：
   primary_pool   = emb_hits[primary]  + kw_hits ∩ primary
   crossover_pool = emb_hits[others]   + kw_hits ∩ others
   
   limit_primary = ceil(limit * (1 - cross_project_ratio))   # 默认 80%
   limit_cross   = limit - limit_primary                      # 默认 20%

3. 评分（保留现有 5 信号 embedding/tag/quality/diversity/business + RRF）：
   对 primary 候选：business 分数 = 1.0
   对 cross 候选  ：business 分数 = 0.5    # 已有的"originals vs generated"业务权重升级为"项目归属"权重

4. 融合 + diversity 后处理：
   按融合 score 降序取前 limit_primary 张 from primary_pool
   按融合 score 降序取前 limit_cross   张 from crossover_pool
   合并、按 score 重新排序输出
```

#### 关键设计选择

**(1) 召回阶段的隔离 vs 融合**

不在召回阶段混合（不构建跨项目大 shard）。每项目单独 top-K 召回，再融合。

为什么：消除"高频项目排队拥挤"问题。原 1 个 200-result 池里漂流可能只占 30 个名额；现在漂流自己有 200 个名额可以挤进 final ranking。

**(2) 跨项目配额，不是评分惩罚**

设了 `cross_project_ratio=0.2` 的硬配额。即使跨项目候选的 embedding 得分高于主项目，也只能拿到 limit*0.2 个名额。

为什么：用户主动来 UGC 活动 A 看图，看到全是 B 项目的图会很困惑。"配额"是业务规则，不是质量信号，应该硬切。

**(3) 业务权重升级**

现有 `business` 信号目前只区分 originals vs generated（0.5 / 1.0）。改成同时编码"项目归属":

```python
business = 1.0 if (project == primary and source_type == 'original')
         else 0.7 if (project == primary and source_type == 'generated')
         else 0.4 if (project != primary and source_type == 'original')
         else 0.2  # cross-project generated
```

这样"主项目原图 > 主项目生成图 > 跨项目原图 > 跨项目生成图"成为评分时的天然偏置。

**(4) 没有 `primary_project_id` 时的退化行为**

```
if primary is None:
    # admin 跨项目，按现状逻辑（合并 shard）；但仍然按项目做 diversity 后处理
    # 避免高频项目占满
    diversity 强制按 project_id 分组，每项目最多 limit/N 张
```

#### 接口形态

```http
POST /open-api/v1/images/match
Authorization: Bearer lk_live_xxx.<secret>

{
  "text": "周末带孩子来漂流，回程路上还能去山地公园玩过山车",
  "limit": 8,
  "strategy": "balanced",
  "diversity": "balanced",

  "scope": {                       // ← 新增段，替代 filters.project_id
    "primary_project_id": "abc",   // ApiKey 绑了哪个就用哪个，body 不能覆盖
    "cross_project_ratio": 0.2     // 0~1。0 = 严格隔离；1 = 完全跨库；默认 0.2
  },

  "filters": {
    "scene": ["山地景观"],
    "source_type": "generated"
  }
}
```

**响应增加**：

```json
{
  "matches": [
    {
      "image_id": "...",
      "rank": 1,
      "project_id": "abc",            // ← 新增，告诉调用方这张图属于哪个项目
      "is_primary_project": true,     // ← 新增，便于 UGC 端展示「相关推荐」标签
      ...
    }
  ],
  "scope": {
    "primary_project_id": "abc",
    "cross_project_count": 1,         // ← 实际跨项目命中几张
    "primary_project_count": 7
  }
}
```

UGC 前端拿到 `is_primary_project=false` 的图，可以打个「相关项目」角标，告诉用户"你可能也对这个感兴趣"——把"互荐"做成产品语言而不是隐藏的副作用。

#### 调试控制

试匹配 playground UI 加：

| 控件 | 默认 | 调试用途 |
|---|---|---|
| 候选范围 | 仅主项目 / 主项目优先 / 跨项目均衡 | 三档预设，对应 cross_ratio = 0 / 0.2 / 0.5 |
| 主项目下拉 | 当前项目 | 切到其它项目模拟 UGC 调用 |

## 第二部分：部署架构（本地 sidecar → 公网 UGC）

### 4. 现状

| 资源 | 位置 | 大小 |
|---|---|---|
| sidecar (FastAPI) | 操作员 MacBook，`localhost:7879` | — |
| SQLite DB | `~/.lintu/lintu.db` | 数百 MB |
| 图片原图 + 生成图 | 操作员磁盘 | 数 GB ~ 数十 GB |
| Embedding 向量 | DB BLOB 列 | 每张 8KB（2048 dim float32） |
| OSS 已同步图 | 阿里云 OSS bucket `your-bucket` | 部分（按 sync 状态） |
| UGC 前端 | `https://ugc.example.com` | 公网 |

**问题**：UGC 前端在公网，sidecar 在 NAT 后的本地机器，**不可直接调通**。

`LINTU_MODE=server` 已在代码里预留（main.py:101-119 + middleware/auth），但仅切了路由开关，还没有做"远端部署"这件事。

### 5. 方案对比

#### 方案 A：本机直连（隧道暴露）

操作员开 Cloudflare Tunnel / ngrok / frp，把本地 7879 暴露成公网地址。

| 维度 | 评估 |
|---|---|
| 实现成本 | 极低，隧道工具 + DNS 配一次 |
| 可用性 | 操作员关机 → UGC 全挂；隧道断 → UGC 全挂 |
| 性能 | 经过隧道一跳，匹配延迟 +50~200ms |
| 数据安全 | 本机暴露公网，需要严格的 ApiKey 鉴权（已有），但攻击面变大 |
| 适合阶段 | **MVP / 内部联调** |

#### 方案 B：sidecar 整体上云（headless server）

把 sidecar 完整部署到云服务器，DB、图片、embedding 都搬上去。本地 Electron 改成"远程客户端"，所有写操作都打到云端。

| 维度 | 评估 |
|---|---|
| 实现成本 | 中等。需要做：数据迁移工具、Electron 配置远程 endpoint、文件存储改 OSS |
| 可用性 | 高（云盘 + 云数据库） |
| 操作员体验 | 失去"本地优先"，每次打标 / 生图都是远程；网络差时极卡 |
| 成本 | 持续云开销（CPU + 存储 + 流量）；GPU 成本（如果要在云端跑 embedding） |
| 适合阶段 | **如果业务做大、有专职运维**；目前显然过度 |

#### 方案 C：分层架构 —— 本地控制面 + 云端只读数据面（推荐）

操作员的本地 sidecar 仍然是"工作台"：扫描 / 打标 / 生图 / 调试，所有重活在本地。每次有图被打标 / 生成 / embedding 完成后，**额外把元数据 + embedding 同步到云端只读 API**。云端只服务 UGC 的"查询请求"。

```
┌─────────────────────┐                    ┌───────────────────────────┐
│ 操作员 MacBook       │                    │ 云端边缘服务 (Edge)         │
│                     │                    │  - PostgreSQL (元数据 + 向量) │
│ Local Sidecar       │ ──── 单向同步 ─────▶│  - HTTP API (/open-api/v1) │
│ - 打标 / 生图        │  (新增 sync worker) │  - ApiKey 鉴权 (复用代码)   │
│ - 试匹配 (本地全功能) │                    │  - 只读，不能写            │
│ - SQLite + 文件      │                    │                          │
└─────────────────────┘                    └───────────────────────────┘
                                                        ▲
                              ┌─────────────────────────┘
                              │
                    ┌──────────────────┐
                    │ 阿里云 OSS         │
                    │ (图片二进制 CDN)   │
                    └──────────────────┘
                              ▲
                              │ 直连 CDN URL
                    ┌──────────────────┐
                    │ UGC 前端 (公网)   │
                    │ ugc.longchantech │
                    └──────────────────┘
```

**核心要点**：

1. **图片二进制不动**：UGC 拿到的 image URL 已经是 OSS CDN 直链（现有 `_public_url_for_match` 就是这么干的），完全不经 sidecar
2. **同步的只是"知识"**：image metadata (id, project_id, file_name, size, source_type, tags, description, blur_score, generation_metadata) + embedding 向量 + cdn_path
3. **同步是单向的**：本地是 source of truth，云端是 read replica。云端不能改任何东西，UGC 写入（像 track-usage / match-feedback）的事件单独存在云端表，定期回流到本地做分析
4. **带宽友好**：embedding 8KB/图 + 元数据 ~2KB/图 ≈ 10KB，3500 张 ≈ 35 MB，几秒钟同步完
5. **数据库选型**：云端用 PostgreSQL + pgvector 比 SQLite 合适（虽然代码里 `_apply_image_filters` 用了 SQLite-only 的 `json_extract`，需要小改）

**部署组件**：

| 组件 | 实现 | 复杂度 |
|---|---|---|
| 云端 sidecar | 现有 sidecar 代码 + `LINTU_MODE=server` + Postgres adapter | 中等 |
| 本地 → 云端同步 | 新写一个 `sync_worker.py`，类似现有 `oss_worker`，监听 image 增改事件 | 低 |
| 部署 | 阿里云 ECS 1 台 + RDS PG 1 台 + Docker | 低 |
| DNS | 一个 `api.example.com` 子域 | 低 |
| ApiKey 体系 | 完全复用现有 `api_keys` 表 + `AuthMiddleware`；同步表数据即可 | 几乎 0 |

**改动量预估**：

| 项 | 工时 |
|---|---|
| 新增 `sync_worker.py`（监听 image / tag / api_key 表变更，POST 到云端 `/internal/sync`） | 4h |
| 云端 sidecar 加 `/internal/sync` 写接口（仅接受本地 sidecar 凭证） | 2h |
| Postgres adapter（替换 `json_extract` 为 `->>'..'`，几个 SQL 函数差异） | 4h |
| 部署脚本 + Docker compose | 3h |
| 端到端联调 | 4h |
| **合计** | **≈ 17h（2 人天）** |

#### 方案 D：纯 Serverless （函数计算 + 向量数据库）

把 match 逻辑搬到阿里云函数计算 + 用阿里云 OpenSearch 向量版做检索。本地只是 ETL。

| 维度 | 评估 |
|---|---|
| 实现成本 | 高，要重写 match 链路适配向量服务的 SDK |
| 可用性 | 极高 |
| 成本 | 调用量不大时几乎免费；调用量大了贵 |
| 锁定 | 强绑定阿里云 |
| 适合阶段 | 业务跑稳后可以演进到这里 |

### 6. 推荐路径

**Stage 0 · 现在（2 周内）**：方案 A 隧道 + 方案 C 的客户端代码准备
- Cloudflare Tunnel 或 ngrok 把本地 sidecar 拉到 `staging-api.example.com`
- UGC 联调用，操作员保证白天开机
- 这期间把方案 C 的 `sync_worker` 写好但不上线

**Stage 1 · UGC 上线（1 个月内）**：方案 C 全量部署
- 云端 ECS + RDS 上线
- 切流，关掉隧道
- 本地→云端单向同步 24/7

**Stage 2 · 业务规模化（半年后）**：按需引入方案 D 的某些组件（向量数据库托管 / CDN 加速）

### 7. 鉴权 / 多租户在分层架构里的位置

云端仍然走现有 ApiKey 体系：

- ApiKey 绑定 `project_id`（前面提到的改动）→ AuthMiddleware 强制 scope
- ApiKey 数据从本地同步到云端（每次本地创建 / 改 / 删 key 时推送）
- 云端 `api_request_logs` 单独存（不回流，定期 export 给本地做分析）

UGC 前端通常**不直接持有 ApiKey**（H5 把 secret 暴露在前端 JS 里有风险）。两种推荐做法：

1. **UGC 自己有后端**：后端代理调用 `https://api.example.com/...`，把 ApiKey 放在后端 env 里
2. **没有后端纯 H5**：发短期的 JWT，UGC 用 JWT 换访问，JWT 过期前可调用受限的端点（仅 read，不能 batch:write）

PRD 第五节其实已经写过这个，落地时按现有方案走。

## 附录 · 关键技术决策汇总

| 决策点 | 选择 | 理由 |
|---|---|---|
| 跨项目搜还是隔离 | **主项目优先 + 配额跨项目** | 配合"互荐"业务用例 |
| 调用方传 project_id | **不允许，由 ApiKey 绑定** | 防漏传 / 防伪造 / 多租户隔离 |
| 召回时机 | **每项目分别 top-K，再融合** | 消除高频项目占位偏置 |
| 跨项目占比 | **配额硬切（默认 20%）** | 业务规则不该靠评分软抗 |
| 业务权重 | **升级为项目归属编码** | 让"主项目"在评分阶段也被认知 |
| 部署形态 | **本地控制面 + 云端只读数据面** | 操作员保留本地体验，UGC 拿到生产级服务 |
| 同步粒度 | **元数据 + embedding 推到云端，图片不动** | 图片走 OSS CDN，sidecar 只管 metadata |
| 云端数据库 | **PostgreSQL + pgvector** | SQLite 不适合云端共享读 + 向量查询效率 |
| MVP 桥接 | **Cloudflare Tunnel** | UGC 联调期间过渡，1-2 周即弃用 |
