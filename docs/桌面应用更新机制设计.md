# 桌面应用更新机制设计

> 状态：**待落地**（仅设计，未开发）
> 创建日期：2026-04-29
> 上下文：v0.2 已完成 Windows 安装包打包（NSIS + 自签代码签名 + GitHub Actions CI），下一步要解决"用户装上之后怎么收到新版本"。

---

## 1. 当前状态

- **分发**：`apps/electron/release/灵图-Setup-0.1.0-x64.exe`，用 NSIS 打的本地安装包，227 MB
- **签名**：自签证书 `CN=Longchan Tech, O=Longchan Tech, C=CN`（5 年有效期），存于 `apps/electron/build/codesign.pfx`（已 gitignore）
- **CI**：`.github/workflows/build-windows.yml` 在 push tag / 改 `apps/**` 时自动产出签名安装包，artifact 形式存 30 天
- **更新机制**：**无**。用户装上之后，要拿新版只能我们手动把新 .exe 发给他、他重装。NSIS 已配 `deleteAppDataOnUninstall: false`，重装会保留本地数据库和工作区。

---

## 2. 三种更新路径对比

按"用户体验糙→精"和"实现复杂度低→高"递增：

| | A. 手动重装 | B. 应用内"检查更新"按钮 | C. 完全自动更新 |
|---|---|---|---|
| **用户感知** | 每次拿新 .exe 自己装 | 点设置里按钮触发更新 | 后台静默下载，下次启动一键应用 |
| **更新率（经验值）** | <30% | 60-80% | >95% |
| **app 端代码量** | 0 | ~50 行 | ~80 行 |
| **服务端基础设施** | 无 | 一个稳定 URL + 版本元数据 | 同 B |
| **强制更新能力** | 无 | 可（启动时检查） | 可（灰度+强制） |
| **灰度发布** | 不支持 | 不支持 | 可选 |
| **代码签名要求** | 不强 | 强 | 强（Windows 拒绝应用未签名增量） |
| **适合场景** | 内部 5-10 人 demo | 20-100 个外部测试用户 | 正式商用产品 |
| **工时估算** | 0 | 0.5 人天 | 1.5-2 人天 |

## 3. 基础设施选型

路径 B / C 都需要一个**稳定 URL** 放：
- 各版本的 .exe 安装包
- `latest.yml`（描述最新版本号、文件 sha512、发布日期）

### 候选对比

| 选项 | 适合度 | 说明 |
|---|---|---|
| **阿里云 OSS** | ✅ **首选** | 项目已经在用 OSS 做图床，bucket / RAM 现成，国内 CDN 加速速度快，可绑自定义域名 `update.lintu.app` |
| GitHub Release | ❌ | 仓库私有，外部用户拿不到 token 就 401 |
| 七牛 / 腾讯 COS | ⚠️ 备选 | 跟 OSS 同质，没必要额外接一个云 |
| 自建 nginx | ⚠️ | 要自己运维，没意义 |

### 推荐 OSS 目录结构

```
oss://lintu-releases/
├── windows/
│   ├── latest.yml                          # electron-updater 自动消费
│   ├── 灵图-Setup-0.1.0-x64.exe
│   ├── 灵图-Setup-0.1.0-x64.exe.blockmap   # 增量下载用
│   ├── 灵图-Setup-0.1.1-x64.exe
│   ├── 灵图-Setup-0.1.1-x64.exe.blockmap
│   └── ...
└── mac/                                    # 未来 macOS 也走这套
    ├── latest-mac.yml
    └── ...
```

### `latest.yml` 示例

```yaml
version: 0.1.1
files:
  - url: 灵图-Setup-0.1.1-x64.exe
    sha512: <128-char-base64>
    size: 238273216
path: 灵图-Setup-0.1.1-x64.exe
sha512: <128-char-base64>
releaseDate: '2026-05-15T10:30:00.000Z'
```

这个文件由 electron-builder 在 build 时自动生成，不用手写。

## 4. 路径 B 实现要点（推荐落地起点）

### 4.1 app 端

**安装新依赖**：
```bash
cd apps/electron
npm install electron-updater
```

**main 进程改动**（`apps/electron/src/main/index.ts`）：

```ts
import { autoUpdater } from 'electron-updater'

autoUpdater.autoDownload = false   // 用户点了按钮才下载
autoUpdater.autoInstallOnAppQuit = true

ipcMain.handle('check-for-updates', async () => {
  return await autoUpdater.checkForUpdates()
})

ipcMain.handle('download-update', async () => {
  return await autoUpdater.downloadUpdate()
})

ipcMain.handle('quit-and-install', () => {
  autoUpdater.quitAndInstall()
})

// Forward lifecycle events to renderer
autoUpdater.on('update-available',  info => mainWindow?.webContents.send('updater:available', info))
autoUpdater.on('update-not-available', () => mainWindow?.webContents.send('updater:none'))
autoUpdater.on('download-progress', p   => mainWindow?.webContents.send('updater:progress', p))
autoUpdater.on('update-downloaded', info => mainWindow?.webContents.send('updater:downloaded', info))
autoUpdater.on('error',             e    => mainWindow?.webContents.send('updater:error', e?.message))
```

**preload 加 IPC 桥**（`apps/electron/src/preload/index.ts`）：

```ts
contextBridge.exposeInMainWorld('updaterAPI', {
  checkForUpdates: () => ipcRenderer.invoke('check-for-updates'),
  downloadUpdate:  () => ipcRenderer.invoke('download-update'),
  quitAndInstall:  () => ipcRenderer.invoke('quit-and-install'),
  on: (event: string, cb: (data: any) => void) => {
    ipcRenderer.on(`updater:${event}`, (_e, d) => cb(d))
    return () => ipcRenderer.removeAllListeners(`updater:${event}`)
  },
})
```

**渲染进程**：在"设置"页加一个"检查更新"按钮 + 进度条 UI（约 30 行 React）。

### 4.2 electron-builder 配置

`apps/electron/electron-builder.yml` 加：

```yaml
publish:
  - provider: generic
    url: https://update.lintu.app/windows
    channel: latest
```

或直接用 OSS（需要 electron-builder 的 s3 provider，OSS 兼容 S3 协议）：

```yaml
publish:
  - provider: s3
    endpoint: https://oss-cn-hangzhou.aliyuncs.com
    bucket: lintu-releases
    region: oss-cn-hangzhou
    path: /windows
```

### 4.3 CI 上传步骤

`.github/workflows/build-windows.yml` 末尾加一个 step（用 ossutil 或 aws-cli 走 S3 兼容协议）：

```yaml
- name: Upload to Aliyun OSS
  if: startsWith(github.ref, 'refs/tags/v')
  env:
    AWS_ACCESS_KEY_ID:     ${{ secrets.OSS_ACCESS_KEY_ID }}
    AWS_SECRET_ACCESS_KEY: ${{ secrets.OSS_ACCESS_KEY_SECRET }}
  run: |
    aws s3 cp apps/electron/release/灵图-Setup-*.exe          s3://lintu-releases/windows/ --endpoint-url https://oss-cn-hangzhou.aliyuncs.com
    aws s3 cp apps/electron/release/灵图-Setup-*.exe.blockmap s3://lintu-releases/windows/ --endpoint-url https://oss-cn-hangzhou.aliyuncs.com
    aws s3 cp apps/electron/release/latest.yml                 s3://lintu-releases/windows/ --endpoint-url https://oss-cn-hangzhou.aliyuncs.com
```

需要在 GitHub Secrets 加：
- `OSS_ACCESS_KEY_ID`
- `OSS_ACCESS_KEY_SECRET`

最好用一个**只对 lintu-releases bucket 有写权限**的 RAM 子账号，不要用主 AccessKey。

## 5. 路径 C 在 B 基础上的增量

主要差别：

1. **启动时静默检查**：`autoUpdater.checkForUpdates()` 在 `app.whenReady()` 末尾自动调，不需要用户点按钮
2. **后台静默下载**：`autoUpdater.autoDownload = true`
3. **下次启动时应用**：`autoUpdater.autoInstallOnAppQuit = true`（B 已经开了，C 继续用）
4. **灰度发布**：`latest.yml` 拆成 `latest.yml`（10% 用户）和 `stable.yml`（90% 用户），app 启动时按 user_id hash 决定读哪个

### 灰度发布的简易实现

```ts
import { createHash } from 'crypto'
import { machineIdSync } from 'node-machine-id'

const userBucket = parseInt(createHash('md5').update(machineIdSync()).digest('hex').slice(0, 8), 16) % 100
autoUpdater.channel = userBucket < 10 ? 'beta' : 'stable'
```

CI 在打 tag 时上传到 `beta/`，灰度通过后再 `aws s3 cp beta/* stable/`。

## 6. 代码签名跟更新的关系

**Windows 强制签名**：`electron-updater` 在 Windows 上检查更新文件的 Authenticode 签名。如果新版本签名失败 / 跟当前版本不是同一个发布者，**会拒绝应用更新**（这是 Squirrel.Windows / NSIS 的硬性要求，防止中间人替换 .exe）。

含义：
- 自签证书可以做更新链路，**但所有版本必须用同一把证书签**。一旦换证书（比如有效期到了），老版本无法升级到新版本，用户必须手动重装一次（覆盖安装即可，数据保留）
- 自签证书外部用户首次安装仍然有 SmartScreen 警告。买 EV 证书是消除该警告的唯一办法
- EV 证书过期后续期，新签名的版本对老用户**自动更新会失败**（一次性问题）。可以通过同时保留旧证书签名 + 双签名缓解，但不本质解决

## 7. 决策树（送给未来的自己）

```
当前用户量是多少？

├─ < 10 个内部测试 → 路径 A，先发 .exe 文件
│
├─ 10-50 个外部测试 / 内部正式
│   │
│   ├─ 更新频率 > 1 次/月 → 路径 B
│   └─ 更新频率 < 1 次/月 → 继续 A，每月发一次邮件
│
├─ 50-500 付费用户
│   │
│   ├─ 接受 SmartScreen 警告 → 路径 B + 自签证书
│   └─ 不接受警告 → 路径 B + EV 证书（先买证书再上线）
│
└─ > 500 商用产品 → 路径 C + EV 证书 + 灰度发布
```

## 8. 待确认事项

要正式决定上路径 B/C 时，需要回答：

1. **目标用户规模**：当前 / 6 个月 / 1 年的预期用户数？
2. **更新发布节奏**：周更 / 月更 / 季度更？
3. **OSS 存储成本预算**：每月发 1 个新版本 = ~250 MB；保留近 6 个版本 = 1.5 GB OSS 存储 ≈ ¥0.18/月。下载流量按 100 个用户全部更新一次 = 25 GB ≈ ¥6/次。可忽略。
4. **是否绑定自定义域名**：建议绑 `update.lintu.app`（CNAME 到 OSS bucket），后续换 CDN 服务商不影响 app 端配置
5. **代码签名证书策略**：自签持续 / 短期内购 EV / 还是观望？
6. **是否需要回滚机制**：发现新版本有重大 bug 时，能不能让用户回到上一版？（实现成本：低，把 `latest.yml` 改回旧版本号即可）
7. **是否需要强制更新**：当某版本有安全 bug 时，能否阻止旧版本继续启动？
