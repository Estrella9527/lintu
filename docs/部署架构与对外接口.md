# 灵图 · 部署架构与对外接口设计

> 本文档面向外部协作者（架构 / 后端 / DevOps），自包含，不需要预先了解灵图代码库。
>
> **背景一句话**：灵图是一个景区图片 AI 生产平台，目前以桌面应用形式跑在运营人员的本机上，需要把它的"匹配能力"接出来给公网 UGC 平台调用。
>
> 写于 2026-04-28。版本 v0.1。

---

## 1. 系统是什么

灵图（Lintu）当前形态：

- **桌面应用**：Electron 壳子 + React 前端 + 嵌入的 Python sidecar（FastAPI + SQLite + 本地图片文件夹）
- **运行位置**：景区运营人员的 MacBook，sidecar 监听 `localhost:7879`
- **核心数据**：
  - 图片本身（原图 + AI 生成图）：本机文件系统
  - 元数据（描述、标签、blur 评分等）：本机 SQLite
  - 跨模态向量（用于文图匹配）：本机 SQLite BLOB 列，每条 8KB（2048 维 float32）
- **图片对外分发**：通过阿里云 OSS。运营人员触发同步后，图片二进制上传到 bucket，CDN URL 公网可访问
- **AI 模型链路**（重要 — 文图匹配的前提是同一个 embedding 模型同时跑文本和图像）：
  - **图像 + 文本 embedding**：火山豆包 `doubao-embedding-vision-251215`（OpenAI 兼容协议，通过中转 relay 调用）。**不是 Gemini**，Gemini 文本和图像走的是不同 embedding 空间，技术上不能用于跨模态匹配
  - **打标视觉模型**：豆包 Doubao Vision Pro / Lite 之类
  - **生图模型**：豆包 Seedream / Gemini-2.5-image / GPT-Image 等（按 task_type 选）
  - **查询扩展（可选）**：用任意 LLM（豆包 doubao-seed-2-0-lite / Gemini-2.0-flash），对延迟不敏感时启用

下游使用方 **UGC 平台**：

- URL：`https://ugc.example.com`
- 形态：公网 H5 站，景区运营 / 游客 在上面发布带 AI 关联内容的活动帖
- 需求：拿到一段文本（活动描述 / AI 生成的相关推荐文案），返回最相关的 N 张图作为帖子封面 / 配图
- 多景区：示例景区A、山地公园、后续会更多。每个 UGC 活动都属于某个景区

## 3. 已经做的准备工作

代码层面已经为"对外服务"留了脚手架：

### 3.1 双模式启动

`sidecar/config.py`：

```python
LINTU_MODE = os.environ.get("LINTU_MODE", "electron").lower()
# electron — 跟桌面 app 绑定，/api/* 全开放
# server   — 公网部署，/api/* 关闭，只暴露 /open-api/v1/*
```

### 3.2 鉴权 / 限流 / 审计中间件

`sidecar/middleware/`：

- `auth.py` — `Authorization: Bearer lk_live_xxx.<secret>`，SHA256 校验
- `rate_limit.py` — 内存滑动窗口，per_minute / per_day
- `quota.py` — 每日配额持久化到 DB
- `audit.py` — 全请求落库到 `api_request_logs` 表

### 3.3 已对外的 API 端点

`/open-api/v1/*` 一共 10 个端点，覆盖：

| 端点 | 用途 |
|---|---|
| `GET /health` | 健康检查（公开） |
| `GET /images` | 图片列表（筛选、分页） |
| `GET /images/{id}` | 单张详情 + 标签 |
| `GET /images/{id}/derivatives` | 该种子的所有衍生 |
| `GET /images/{id}/file` | 图片文件流（在 CDN 之前的回退） |
| `POST /images/match` | **本文重点：文图匹配** |
| `POST /images/similar` | 图找图（嵌入相似） |
| `POST /images/{id}/track-usage` | UGC 反馈（"用户选了这张"） |
| `GET /tags` | 标签分布 |
| `GET /stats` | 库存统计 |

### 3.4 ApiKey 管理 UI

桌面应用已有"分发中心 → API Keys"页面，可以创建 / 轮换 / 停用 key。**当前还没有项目绑定字段**（本文档需要新增）。

## 4. 部署方案对比

四个方案，按从简单到复杂排列。

### 方案 A · 隧道（Cloudflare Tunnel / ngrok / frp）

把本机 `localhost:7879` 用隧道工具暴露到公网。

```
本机 sidecar  ←  隧道客户端  ─── HTTPS ───→  Cloudflare 边缘  ─── HTTPS ───  UGC
              (cloudflared)
```

| 维度 | 评估 |
|---|---|
| 实现成本 | 极低，1 小时完成 |
| 可用性 | 操作员关机或断网 → 全挂 |
| 性能 | 多一跳，匹配延迟 +50~200ms |
| 安全 | 本机暴露公网，攻击面变大；ApiKey 鉴权已有，但 sidecar 漏洞会直接影响生产 |
| 适合阶段 | **MVP 联调期 / 线下演示** |

### 方案 B · sidecar 整体上云

把 sidecar 全部搬到云服务器，DB / 图片 / embedding 都搬上去。本地 Electron 改成"远程客户端"，所有写操作（打标 / 生图）都打到云端。

```
本地 Electron  ─── HTTPS ───→  云端 sidecar (full)  ←─── HTTPS ───  UGC
                                  - 云端 DB
                                  - 云端图片存储
                                  - 云端 GPU（如果要跑 embedding）
```

| 维度 | 评估 |
|---|---|
| 实现成本 | 中等。需做：数据迁移工具、Electron 改远程模式、文件存储改 OSS |
| 可用性 | 高（云盘 + 云数据库） |
| 操作员体验 | **失去本地优先**，每次打标 / 生图都是远程；网差时极卡 |
| 成本 | 持续云开销（CPU + 存储 + 流量）；GPU 成本高 |
| 适合阶段 | 业务做大 + 有专职 SRE 时；目前过度 |

### 方案 C · 控制面 / 数据面分离 ⭐ 推荐

**核心思想**：本地 sidecar 是 "工作台"（控制面），云端是 "只读副本"（数据面）。

```
┌───────────────────────────────────┐
│  本地 sidecar（控制面）             │
│  - 扫描原图、打标、生图、调试         │
│  - SQLite + 本地文件（source of truth）│
│  - 完整功能，全部在本地完成           │
└─────────────┬─────────────────────┘
              │
              │ 单向同步：每次有图打标 / 生成 / embedding 完成后，
              │ 把元数据 + 向量 + cdn_path 推送到云端
              │ （不推图片二进制，那个由 OSS 同步走另一条路）
              ▼
┌───────────────────────────────────┐
│  云端 Edge（数据面）                 │
│  - PostgreSQL + pgvector           │
│  - 灵图 sidecar 代码 + LINTU_MODE=server│
│  - 只读 /open-api/v1/* 端点         │
│  - 鉴权 / 限流 / 审计中间件复用本地代码 │
└─────────────┬─────────────────────┘
              │
              │ HTTPS + ApiKey
              ▼
┌───────────────────────────────────┐
│  UGC 前端                          │
│  ugc.example.com              │
└─────────────┬─────────────────────┘
              │
              │ 直接拉图（CDN）
              ▼
┌───────────────────────────────────┐
│  阿里云 OSS / CDN                   │
│  图片二进制（不经过任何 sidecar）     │
└───────────────────────────────────┘
```

**关键设计点**：

#### 4.1 图片二进制不经过 sidecar

UGC 拿到的 image URL 已经是 OSS CDN 直链。例：

```json
{
  "image_id": "xxx",
  "url": "https://your-bucket.oss-cn-hangzhou.aliyuncs.com/i/xxx.jpg",
  "thumbnail_url": "https://your-bucket.oss-cn-hangzhou.aliyuncs.com/i/xxx_300.jpg"
}
```

云端 sidecar 只返回 URL，不代理流量。这就解决了"图片传输成本 / 带宽"问题。

#### 4.2 同步只是元数据 + 向量

每张图需要同步的字段（约 2KB）：
- `image_id`, `project_id`, `file_name`, `width`, `height`, `source_type`
- `description`, `tags[]`（来自本地打标）
- `blur_score`, `tag_status`
- `generation_metadata`（如果是 AI 生成）
- `cdn_path`（OSS 同步成功后填）
- **`embedding`**（关键，约 8KB float32）

3500 张图 × 10KB ≈ **35 MB**，初次全量同步几秒钟。增量同步以单条计，可忽略。

#### 4.3 云端 sidecar 几乎复用现有代码

- 启动时设 `LINTU_MODE=server` → `/api/*` admin 路由自动关闭，只暴露 `/open-api/v1/*`
- 鉴权 / 限流 / 审计中间件原样工作
- DB adapter 需要小改：现有 SQLite-only 的 `json_extract` 替换成 PostgreSQL 的 `->>'..'`
  - 影响：`routers/images.py` 里 `_apply_image_filters` 一处
- 不需要 GPU；embedding 由本地算完推上来即可

#### 4.4 同步组件：sync_worker

新增一个 `sync_worker.py`，挂在本地 sidecar 进程里：

- 监听 `image` 表变更（INSERT / UPDATE）
- 累积变更队列，每 30s 或满 100 条触发一次推送
- 调用云端的 `POST /internal/sync/images`，云端用单独的 `INTERNAL_SYNC_TOKEN`（不走公开 ApiKey 体系）
- 失败重试 + 持久化队列（用一张 `sync_queue` 表，类似现有 `oss_sync_jobs`）

#### 4.5 ApiKey 也走同步

- 本机 ApiKey 表的写操作触发推送
- 云端 ApiKey 表是只读副本（运营在桌面创建 key → 同步到云 → UGC 用 key 调云端）

| 维度 | 评估 |
|---|---|
| 实现成本 | 中。预估 2 人天 |
| 可用性 | 高（云盘） |
| 操作员体验 | 完全保留本地优先 |
| 成本 | 一台小 ECS（2C4G）+ RDS PG（最低规格）≈ ¥200/月 |
| 适合阶段 | **UGC 正式上线** |

### 方案 D · Serverless + 托管向量库

云端 sidecar 替换为函数计算 + 阿里云 OpenSearch 向量版。

| 维度 | 评估 |
|---|---|
| 实现成本 | 高，要重写 match 链路适配向量服务 SDK |
| 可用性 | 极高 |
| 成本 | 调用量小时几乎免费；调用量大了贵 |
| 锁定 | 强绑定阿里云 |
| 适合阶段 | 业务规模化（>10 万次/天匹配调用）后 |

### 4.6 推荐路线

```
Stage 0  ──  方案 A 隧道（联调期）─────────────┐
            ↓                              │
Stage 1  ──  方案 C 全量部署（UGC 正式上线）  │  逐步替换
            ↓                              │
Stage 2  ──  方案 D 局部托管化（按需）      ◄┘
```

- **现在 ~ UGC 联调阶段**：方案 A，运营人员保证白天开机，UGC 后端代理调用 `staging-api.example.com`
- **UGC 正式上线（1 个月内）**：方案 C 切流，撤掉隧道
- **业务规模化（半年后）**：按瓶颈引入方案 D

## 5. 接口设计

### 5.1 鉴权

所有 `/open-api/v1/*` 端点（除 `/health`）需要：

```http
Authorization: Bearer lk_live_xxx.<secret>
```

`lk_live_xxx` 是公开的 key_id；`<secret>` 是创建时一次性返回的 plain-text secret，**之后无法再查看**（DB 只存 SHA256）。

UGC 前端不应直接持有 secret（H5 暴露在前端 JS 不安全）。两种推荐做法：

1. **UGC 有自己的后端**：后端代理调用，secret 在后端 env 里
2. **纯静态 H5**：发短期 JWT，UGC 用 JWT 换访问，定期换签

### 5.2 ApiKey 必须绑项目（待做）

**这是本次新增的关键约束**。当前 ApiKey 表没有 `project_id` 列，需要：

```sql
ALTER TABLE api_keys ADD COLUMN project_id TEXT REFERENCES projects(id);
```

`AuthMiddleware` 收到请求后：

1. 校验 ApiKey 有效
2. 读取 key 的 `project_id`
3. 把 `project_id` 注入 `request.state.bound_project_id`
4. 业务路由强制读 `state.bound_project_id`，**忽略 body 里的项目字段**

理由：
- 防漏传 / 防伪造 / 防越权
- UGC 拿到的是"示例景区A key"，调出来的图永远在示例景区A范围内（加跨项目互荐配额，详见匹配策略文档）
- 如果某把 key 真的需要跨项目（极少数运营 / admin 用例），创建时不绑 `project_id`，调用方可以传 / 也可以不传

### 5.3 核心匹配端点

```http
POST /open-api/v1/images/match
Authorization: Bearer lk_live_xxx.<secret>
Content-Type: application/json

{
  "text": "周末带孩子来漂流，回程路上还能去山地公园玩过山车",
  "limit": 8,
  "strategy": "balanced",       // precise | balanced | diverse，可选
  "diversity": "balanced",      // strict | balanced | none，可选
  "filters": {                  // 可选
    "scene": ["山地景观"],
    "season": ["秋季"],
    "source_type": "generated"  // generated | original
  }
}
```

**注意 body 里没有 `project_id`** —— 由 ApiKey 决定。

**响应**：

```json
{
  "matches": [
    {
      "image_id": "xxx",
      "rank": 1,
      "score": 0.823,
      "embedding_sim": 0.78,

      "thumbnail_url": "https://your-bucket.oss-cn-hangzhou.aliyuncs.com/i/xxx_300.jpg",
      "cdn_synced": true,
      "file_name": "DJI_20240612_漂流主入口.jpg",
      "width": 1920,
      "height": 1280,
      "source_type": "generated",
      "project_id": "lpx",                  // ★ 新增
      "is_primary_project": true,           // ★ 新增（属于 ApiKey 绑定的项目）
      "description": "夏日漂流的入口...",
      "tags": { "scene": ["水域"], "facility": ["漂流"] },
      "matched_tags": [{ "dimension": "facility", "value": "漂流" }],

        "embedding": 0.78,
        "tag": 0.65,
        "quality": 0.42,
        "diversity": 0.10,
        "business": 1.0
      }
    },
    ...
  ],
  "scope_decision": {                       // ★ 新增段，告诉调用方系统怎么决策的
    "primary_project_id": "lpx",
    "auto_detected_weights": {
      "lpx": 0.72,
      "msp": 0.28
    },
    "selected_quota": {
      "lpx": 6,

  "took_ms": 87,

```

UGC 前端可以根据 `is_primary_project=false` 给图片打"相关推荐"角标，把跨项目互荐做成产品语言。

### 5.4 反馈端点（很重要）

```http
POST /open-api/v1/images/{id}/track-usage
{
  "request_id": "req_xxx",       // 来自 match 响应里的 request_id
  "rank": 3,
  "was_chosen": true             // 用户最终选了这张
}
```

UGC 在用户选定封面时调一下，灵图用这些数据计算"命中率"、找出"难召回"的 query，反哺策略调优。

### 5.5 完整端点列表

UGC 上线必备：

| 端点 | 用途 | 鉴权 scope |
|---|---|---|
| `GET /health` | 健康检查 | 公开 |
| `POST /images/match` | **核心：文图匹配** | `images:match` |
| `POST /images/similar` | 图找图 | `images:match` |
| `POST /images/{id}/track-usage` | 用户行为反馈 | `images:read` |
| `GET /images/{id}` | 单张详情 | `images:read` |
| `GET /tags` | 标签字典（前端 UI 用） | `tags:read` |

## 6. 接口变更兼容性

如果未来要新增字段：

- **响应字段加新 key**：兼容（旧调用方忽略新字段）
- **请求体加 optional 字段**：兼容（缺省值）
- **请求体改字段语义**：不兼容，需要 v2 版本路径
- **删除字段**：不兼容，先 deprecate 再下线

`/open-api/v2/*` 路径预留位置，目前没有。

## 7. 数据流总结（一张图）

```
┌──────────────┐    打标/生图     ┌──────────────┐
│  本地 sidecar  │  ─────────►    │  本地 SQLite   │
│              │                 │  + 图片 + 向量  │
└──────┬───────┘                 └───────┬──────┘
       │                                 │
       │ OSS 上传图片                     │ sync_worker 监听变更
       │                                 │ 推送元数据 + 向量
       ▼                                 ▼
┌──────────────┐                 ┌──────────────┐
│  阿里云 OSS    │                 │  云端 PG       │
│  图片 + CDN   │                 │  元数据 + pgvector│
└──────┬───────┘                 └───────┬──────┘
       │ 公网 GET 图片                    │ 公网 POST 匹配
       │                                 │
       └────────────┬────────────────────┘
                    ▼
            ┌──────────────┐
            │  UGC 前端      │
            └──────────────┘
```

写路径：本地为主。
读路径：云端只读副本服务。
图片：从来不经过 sidecar，全部走 CDN。

## 9. 待确认

外部协作者参与时需要拍板的事项：

1. **云端机器规格**：建议阿里云 ECS 2C4G + 50GB SSD + RDS PG 最低规格（共享型 1C2G 100GB），月成本 ~¥200。要不要走专有网络（VPC）？
2. **域名**：`api.example.com` 子域指向云端 ECS，需要配置 SSL（Let's Encrypt 或阿里云免费证书）
3. **云端 sidecar 进程管理**：systemd / Docker / supervisor，倾向 Docker compose
4. **同步可靠性**：本机离线时本地 sidecar 累积事件，回归后批量推；要不要保留 last 7 天的事件流防回滚？
5. **JWT 方案**：UGC 如果纯 H5 不带后端，需要灵图额外提供"短期 token 颁发"端点，OAuth2 / 自研都可以
6. **观测**：云端是否需要接 Prometheus / Sentry / 阿里云 ARMS？
