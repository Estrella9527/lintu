# 灵图 · 数据云端化（多设备同步）设计方案 — #203 / PR-4

> 状态：**方案待定**（先定架构岔路，再细化落地）
> 日期：2026-06-08
> 背景：当前 cloud-sync 是**单向 本地→云端 推送**，云端只作 UGC 匹配只读副本。
> 本任务要解决的是**同一账号在多台桌面端之间看到同一份数据**。

---

## 0. 现状（必须先认清，避免重复造轮子）

现有链路（`scheduler/cloud_sync_worker.py` + `routers/internal_sync.py`）：

- **方向**：单向。本地桌面端是**唯一真相源**；云端 PG 是 UGC 匹配用的只读副本。
- **触发**：本地任何 image/project/api_key/synonyms/tag_schema/config 写操作 → enqueue `cloud_sync_jobs` → 30s tick 批量 POST 到云端 `/internal/sync/*`。
- **鉴权**：单一共享 `LINTU_INTERNAL_SYNC_TOKEN`（不是用户 token），server-wide 写权限，绕过限流。
- **同步实体**：image（含 tags、embedding）、project、api_key、synonyms、tag_schema、config（仅 embedding/relay 这类非敏感 key）、deletes（墓碑）。
- **缺什么（多设备需要、现在没有的）**：
  1. 云端→本地的**拉取**通道（现在只有 push，没有 pull）。
  2. **冲突处理**（两台设备同时改同一条怎么办）。
  3. **用户/组织数据**本身的同步（users/sessions/orgs/memberships 现在完全不同步）。
  4. 桌面端首次登录/换机时的**全量拉取冷启动**。
  5. 真相权威的归属（现在"本地权威"，多设备下必须有一个仲裁者）。

---

## 1. 核心岔路口（这一步定了，其余全是细节）

多设备同步的本质是「谁是真相源 + 冲突怎么裁」。三条路：

### 方案 A · 云端权威（Cloud-authoritative，推荐）
- 云端 PG 成为**唯一真相源**；桌面端变成"带本地缓存的胖客户端"。
- 写操作：桌面端先写本地（乐观更新）→ 立即同步到云端 → 云端确认。
- 读：桌面端启动/定时 `pull since cursor`，把云端变更合并进本地。
- 冲突：**Last-Write-Wins + updated_at 单调时钟**，云端裁决（云端 updated_at 更大者胜）。
- **图片二进制**：继续走 OSS（已有），桌面端按 `cdn_path` 懒下载缩略图/原图到本地缓存。
- 代价：要给所有同步表加 `updated_at` + 软删 `deleted_at`；要写云端 `GET /internal/sync/changes?since=` 拉取端点；桌面端要写 pull+merge 循环。
- 收益：模型最清晰，多设备一致性最强，未来"网页端只读看库"几乎免费。

### 方案 B · 本地权威 + 单活（Local-authoritative，single active device）
- 仍是本地权威，但**同一账号同一时刻只允许一台"主控端"写**，其余设备只读镜像。
- 换机 = 转移主控权（云端记录 `active_device_id`，加锁）。
- 冲突：靠"只有一台能写"从根上避免，不需要合并算法。
- 代价：交互上要做"主控/只读"状态 + 抢占；多人同时作业体验受限。
- 收益：实现量最小，几乎复用现有 push，只补一个"只读端拉镜像"。

### 方案 C · 双向 CRDT/逐字段合并（最重，不推荐现在做）
- 每字段带向量时钟，真正的多主合并。
- 代价：远超当前收益，3-4 周起，且 SQLite↔PG 双写一致性复杂。
- 结论：**否决**（留作极远期）。

---

## 2. 推荐：方案 A（云端权威），分三期落地

### Phase 1 · 同步基建（后端，~3-4d）
1. 给同步表（image/project/api_key/tag/...）统一加 `updated_at`（已有的复用）+ `deleted_at`（软删替代硬删墓碑）。
2. 云端新增 `GET /internal/sync/changes?since=<iso>&types=image,project,...` → 返回该时间点后的增量（含软删行）。
3. 云端 upsert 改为**带 updated_at 仲裁**：incoming.updated_at ≤ existing.updated_at 时跳过（防回灌覆盖新值）。
4. 用户/组织数据纳入同步：users（脱敏，不含验证码）、orgs、memberships、project_members。

### Phase 2 · 桌面端拉取与合并（~3-4d）
1. 新增 `cloud_pull_worker`：登录后全量冷启动拉取 → 之后按 `last_pull_cursor` 增量。
2. 合并策略：LWW，本地 `updated_at` 旧于云端则覆盖本地；软删行本地也软删。
3. 冲突可观测：合并日志写 audit，冲突项给桌面端一个"以云端为准已覆盖 N 条"的提示。
4. 冷启动 UX：登录后"正在从云端同步数据…"进度条，避免空库误会。

### Phase 3 · 一致性兜底 + 运维（~2d）
1. 周期对账：本地↔云端 行数 + 校验和（按 project 分桶 hash）。
2. 出口 IP 漂移导致 push 失败的问题（正是 #225）→ 同步健康面板，连续失败告警。
3. `scripts/reconcile.py`：一键比对并修复漂移。

预估：**8-10 个开发日**（单人 2 周），与原 plan 估算一致。

## 3. 关键风险

| 风险 | 缓解 |
|---|---|
| SQLite(本地) ↔ PG(云端) 时钟/时区不一致致 LWW 误判 | 统一用 UTC ISO；以**云端写入时刻**为权威 updated_at，不信本地墙钟 |
| 全量冷启动拉取数千图卡 UI | 分页拉 + 后台合并 + 缩略图懒加载（二进制仍走 OSS） |
| 用户/会话数据上云的隐私面 | 只同步必要身份字段，验证码/密钥永不出本地；沿用 internal token + IP 白名单 |
| 出口 IP 漂移（#225 同款）使同步静默失败 | Phase 3 健康面板 + 连续失败告警 + reconcile 脚本 |
| 多端并发改同一条的"丢更新" | LWW 可观测化：覆盖时记 audit，必要时给"版本冲突"提示 |
